# Agent Note: 本地插件目录索引

Status: implemented

[English](2026-08-20-plugin-catalog-local-index.md) | 中文

部分取代：[GitHub 插件目录与内置 AnySearch](2026-08-19-plugin-catalog-and-anysearch.md)（目录发现机制）。

## 问题

npm 服务端搜索按相关性排序，会让刚发布、零下载包的精确名匹配沉底：对 `keywords:dsh-plugin notification`，`dsh-notification` 在约 2526 个结果中排到第 1582 位附近，搜索得分字面为 0；分页式实时搜索在浏览窗口内永远够不到它，空查询目录也只能展示已验证生态中排名靠前的一片，而不是全部。

## 决策

- `pluginManager.catalog` 改为由持久化的全量索引作答，位置在 `$DSH_HOME/cache/plugin-catalog-index.json`：收录每个带 `dsh-plugin` keyword 且最新 manifest 声明了 DSH bundle 或 client 角色的 npm 包。网关每进程加载一次该文件；文件缺失或超过 24 小时就在请求路径之外重建（全量 keyword 范围列表 + 对每个候选用有界并发做一次 latest manifest 校验），通过同级临时文件改名原子写入；schema 带版本号，任何畸形文件都按缺失处理。
- 索引上的排序是本地确定性的：包名相等 > 名字前缀 > 名字子串 > keyword 命中 > 描述命中；多词查询要求每个词都有命中并取各词的最差层级；平局按月下载量再按名称排序。空查询返回覆盖全部已验证集合的下载量排序目录。
- registry 访问保留为兜底与保鲜路径：首次构建完成之前或没有可用文件时，`catalog` 沿用原先的 npm 服务端实时搜索；一次重建失败后进入五分钟退避才允许重试；非空查询的第一页仍会直接向 registry 探测疑似精确包名，因此上次重建之后发布的包依然可被找到。

## 备选方案

- **更深的实时翻页** —— 否决：把第 ~1580 名翻出来意味着每次搜索要走几十页 registry 及其 manifest 校验，且可见性仍由热度加权排序决定。
- **启动时阻塞建索引** —— 否决：会给每次启动增加几十秒量级的 registry 流量，包括从不打开插件管理器的会话，并且新装机器后请求会集中爆发。
- **第三方搜索 API（npms.io）** —— 否决：同样存在热度加权排序问题，还为 npm 已提供的数据引入额外外部依赖。

## 后果

- 精确与前缀匹配不再受下载量影响，确定性靠前展示；空查询目录覆盖完整已验证集合，而非 npm 排序的前几页。
- 每个 host 每天一次重建约消耗 2.5k 次 registry 请求；重建期间旧索引继续应答，并发 host 通过原子改名的最后写入者胜出收敛。
- 重建之间发布的包只能通过精确名探测被找到，直到下次刷新；目前没有手动强制刷新入口。
